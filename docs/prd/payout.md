# Payout & saldo merchant (Model B) [payout] (PRD §4.13)

Baca juga: `../PRD.md` (§0 #14, #14a, #14b), `ledger.md`, `reconciliation.md`, `security.md`, `merchant.md`.

- **Payout:** entitas `payouts` + `payout_items` (transaksi yang dibayarkan). State: `requested → pending_approval → approved → submitted → processing → paid | failed | returned | cancelled`; `unknown` bila timeout (inquiry dulu sebelum retry).
- **Jadwal:** terjadwal (T+N sesuai kebijakan) atau on-demand bila diaktifkan; min/max payout, limit harian; **fee payout: keputusan 14 Okt 2026 — merchant menanggung, dipotong dari nominal payout** (lihat "Keputusan DOKU (14 Okt 2026)" di bawah; angka dari config, jangan dihardcode).
- **Kontrol:** maker-checker (pembuat ≠ penyetuju) di atas ambang; MFA saat approve; hanya rekening terverifikasi (allowlist) + cooling period setelah ganti rekening; idempotency key per payout; payout ≤ `available` dengan lock baris/constraint DB dalam transaksi; limit & alert anomali; semua aksi diaudit; developer tanpa akses approve payout produksi.
- **Eksekusi:** **keputusan 14 Okt 2026: via Kirim DOKU (BI Fast)**, bukan Sub-Account ([KD] sumber dana — lihat "Keputusan DOKU (14 Okt 2026)"); MVP: transfer manual + konfirmasi sampai adapter ada (adapter bank opsional kemudian). Default kode payout = dry-run di non-produksi.
- **Pemisahan dana:** rekening penampung dana merchant terpisah dari operasional [LEGAL]; alert bila `sum(merchant_payable)` > dana di rekening penampung.
- **Rekonsiliasi harian:** ledger ↔ laporan DOKU ↔ mutasi bank PT; selisih → exception.
- **Notifikasi:** merchant diberi tahu payout dibuat/dibayar/gagal + rincian per transaksi (gross, fee, net).

## Keputusan DOKU (14 Okt 2026)

Sumber: jawaban lisan DOKU + catatan resmi di `../integrations/doku.md` §6. Semua yang lisan = **[KD] menunggu konfirmasi tertulis**.

- **Eksekutor = Kirim DOKU** (`POST /snap/v1.1/emoney/transfer-bank`, BI Fast 24/7; ada account-inquiry, balance-inquiry, check-status), **bukan Sub-Account** (QRIS Direct API + sub-account belum terbukti; split dihitung dari net ≠ Biaya Jasa 1% gross). Dipetakan di adapter `internal/gateway/doku` (`Capabilities().Disbursement`); domain tetap gateway-netral (invarian #11).
- **State mesin bertambah:** `approved → submitted → paid | failed | returned`; hasil ambigu (timeout/409/5xx) = **`unknown`** lalu check-status (di-mapping ke `paid`/`failed`/`returned`), tidak pernah retry buta. Idempotency: `partnerReferenceNo` = ID payout, `409` = duplikat. Sebelum transfer: **account-inquiry** (validasi nomor rekening + nama pemilik; nama beda → payout `failed` + dana dikembalikan). **Sudah diimplementasikan 14 Okt 2026** (`internal/payout/execute.go`, migration `0021`, `gateway.Disburser` + adapter DOKU).
- **Fee transfer dibebankan ke merchant, dipotong dari nominal payout:** minta Rp100.000 → terima Rp98.500; Rp1.500 dibukukan sebagai **leg fee tersendiri** (akun ledger `payout_fee_payable` — kewajiban ke gateway, bukan pendapatan), bukan menggerus saldo `merchant_payable` lebih besar dari nominal permintaan. Angka (publik Rp1.500/transfer, belum termasuk PPN) dari config/versioned plan, **jangan dihardcode**; ikuti kontrak [KD]. Fee dari `bank-account-inquiry` (`additionalInfo.feeAmount`), fallback `ERAPAY_PAYOUT_FEE`. Fee ≈ 15% pada minimum Rp10.000 → tinjau angka kebijakan minimum payout.
- **Verifikasi rekening cache-first:** rekening yang sudah `verified` di DB **tidak dicek ulang**; yang belum dikenal divalidasi via **DOKU Bank Account Validation** (Rp500/request, 118+ bank), biaya dibebankan ke merchant; otomatisasi via **config** (default: mati → verifikasi manual oleh Finance seperti v1). Nama hasil validasi tetap dicatat; cooling period `ERAPAY_PAYOUT_COOLING` tetap berlaku.
- **[KD] sumber dana Kirim DOKU:** endpoint `/emoney/...` menyiratkan dari **saldo DOKU**, padahal settlement QRIS dikatakan masuk **rekening bank PT** → tanyakan DOKU: bisa tidak settlement ditahan di saldo DOKU agar Kirim DOKU jadi jalur payout tunggal. Menentukan akun ledger yang di-credit saat `paid` (`cash_doku_clearing` vs `cash_bank_pt`) — jangan diasumsikan sebelum dijawab.
- **Settlement T+1 (12:00–14:00 GMT+7, lisan):** `available` paling cepat T+1 sore → payout on-demand realistis paling cepat T+1; `available` tetap hanya menghitung dana yang sudah settle (lihat `reconciliation.md`).

## Implementasi (v1: dry-run, transfer dicatat manual)
- **State:** `pending_approval → approved → paid`; akhir lain: `failed`, `cancelled` (cancel/reject). Belum ada `submitted/processing/returned/unknown`: tak ada adapter eksekusi, transfer dilakukan Finance lalu dicatat.
- **Rekening:** `POST /v1/bank-accounts` (owner, sesi saja) → `pending_verification`; Finance `POST /v1/admin/bank-accounts/{id}/verify` (pembuat ≠ verifikator, juga CHECK DB). Nomor rekening dienkripsi AES-256-GCM (terikat ke id baris), API hanya mengembalikan `••••last4`. `bank_code` **harus kode BI bank yang didukung Kirim DOKU** (125 bank, `internal/bank/banks.go`; daftar via `GET /v1/banks`, form web berupa dropdown — "BCA" ditolak, kode yang benar `014`). Cooling period setelah verifikasi (`ERAPAY_PAYOUT_COOLING`, default 24h). Rekening tak bisa dinonaktifkan selama ada payout terbuka. Verifikasi otomatis cache-first lihat "Keputusan DOKU (14 Okt 2026)".
- **Uji produksi (probe `cmd/kdtest`, tanpa ledger/domain):** `balance` (gratis, cek saldo + bukti kredensial) → `inquiry <rekening PT>` (Rp500, dapat sessionId + feeAmount) → `transfer <sessionId>` (uang asli, minimum Rp10.000) → `status <partnerRef>` (membuktikan path + service code). Tidak ada retry otomatis (invarian #3). [?] item yang dijawab empiris: service code, mekanik fee, identitas pengirim badan usaha, `CHANNEL-ID`.
- **Request:** `POST /v1/payouts` + `Idempotency-Key` (sesi dashboard, bukan API key). Satu transaksi: kunci baris merchant (`FOR NO KEY UPDATE`) → cek limit (min/max/harian rolling 24h) → cek `available` → insert → **reservasi ledger** `Dr merchant_payable / Cr payout_in_transit`. Maka dua request paralel tak bisa melampaui saldo, dan `available` turun seketika.
- **Approve (checker):** `POST /v1/admin/payouts/{id}/approve` (role `finance`), pemohon tak boleh approve (kode + CHECK DB). Reject/cancel/mark-failed melepas reservasi (`Dr payout_in_transit / Cr merchant_payable`).
- **Eksekusi:** `GET /v1/admin/payouts/{id}/destination` (hanya payout `approved`, diaudit, `no-store`) memberi nomor rekening ke Finance; setelah transfer: `POST .../mark-paid {bank_reference}` → `Dr payout_in_transit / Cr cash_bank_pt`, sekali (dedup key + status). Ulangi dengan referensi sama = no-op; referensi lain = 409. **Via executor (Kirim DOKU, 14 Okt 2026):** `POST /v1/admin/payouts/{id}/execute` → inquiry → claim (`approved→submitted`, `gateway`, `fee_amount`) → transfer (nominal − fee); `POST .../check-status` → `paid`/`failed`/`returned` (menunggu/ditolak = tidak berubah). Kedua endpoint butuh permission `payout:execute`; tanpa disburser → `503 PAYOUT_NO_DISBURSER`; hasil ambigu → `502 PAYOUT_AMBIGUOUS` (status `unknown`, tidak di-lepas, selesaikan via check-status).
- **Gate produksi:** `dry_run` = `ERAPAY_ENV != production`. Di produksi payout ditolak (`503 PAYOUT_DISABLED`) sampai `ERAPAY_PAYOUT_LIVE=1` (go/no-go). Seluruh fitur butuh `ERAPAY_ENCRYPTION_KEY`.
- **Saldo:** `GET /v1/balance` kini memuat `in_payout` (ledger `payout_in_transit`); `payable` tidak lagi memuat dana yang sedang direservasi.
- **Belum:** `payout_items` per transaksi, jadwal otomatis, MFA saat approve, alert anomali, notifikasi ke merchant (webhook outbound untuk event payout, `payout.submitted` sudah ada), rekonsiliasi lapis 2 (mutasi bank). UI admin executor (tombol Execute/Check Status + filter/badge status `submitted`/`unknown`/`returned`) **sudah diimplementasikan 14 Okt 2026** (`apps/web` dashboard/finance/payouts; i18n ID + EN).
